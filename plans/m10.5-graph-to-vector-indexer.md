# M10.5 — Graph-to-Vector Indexer

## Context

Testing M10 revealed the critical gap: the RAG pipeline's vector store starts empty because nothing bridges the Oxigraph triplestore to the vector store. The `Canonicalizer` (M9) can turn triples into deterministic text, and the `EmbeddingProvider` + `VectorStore` (M8/M9) can embed and store them — but there is no orchestration that reads from the graph, canonicalizes, embeds, and upserts.

This milestone adds:
1. An `HttpEmbeddingProvider` that works with any OpenAI-compatible `/embeddings` endpoint (cloud providers, Ollama, LMStudio)
2. A `GraphIndexer` that reads from Oxigraph → canonicalizes → embeds → upserts into the vector store
3. An `index_graph` MCP tool exposing the indexer
4. Shared vector store + embedder state so indexing and retrieval use the same instances

After this milestone, the full loop works: `load_rust_code` → `index_graph` → `agent_query` returns RAG-grounded results.

## Design

### HttpEmbeddingProvider (in `rag_pipeline::embedding`)

Calls any OpenAI-compatible `/v1/embeddings` endpoint.

### GraphIndexer (in `rag_pipeline::indexer`)

Pipeline: SPARQL → RawTriple → canonicalize → embed → upsert

### Shared state in MCP server

Refactor `RagPipeline` to use `Arc<dyn VectorStore>` + `Arc<dyn EmbeddingProvider>` (instead of Box) so indexer and pipeline share instances.

### `index_graph` MCP tool

Exposes GraphIndexer via MCP with optional graph/prefix/batch_size params.

## Implementation Tasks

## Environment Variables (new)

| `EMBEDDING_URL` | (unset) | OpenAI-compatible embeddings endpoint URL |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | Model name sent in request body |
| `EMBEDDING_API_KEY` | (unset) | Bearer token for the endpoint (optional for local) |
| `EMBEDDING_DIM` | `1536` | Embedding vector dimension |
